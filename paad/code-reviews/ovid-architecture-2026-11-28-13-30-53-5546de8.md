## Important Issues

### [I1] Migration-table comment is false; the next version bump will silently skip a migration step
- **File:** `src/game/state/state-validators.js:158-160` (comment), `:169`, `:178-183` (`MIGRATABLE_VERSIONS` / `isVersionCompatible`), `:1062` (`migrateFromV4_1ToV5`)
- **Bug:** `migrateFromV4_1ToV5` sets `state.meta.version = SAVE_FORMAT_VERSION`, while every earlier step writes a literal version (lines 617, 659, 695, 1039). `applyMigrations` runs a step only when `migrated.meta.version === version`. Suppose `SAVE_FORMAT_VERSION` becomes `'6.0.0'` and a developer does only what the comment says, appending `['5.0.0', migrateFromV5ToV6]`. A 1.0.0–4.1.0 save then leaves the 4.1 step already stamped `'6.0.0'`, so the 5→6 step never runs. On main, `isVersionCompatible` hard-coded `SAVE_FORMAT_VERSION === '5.0.0'`, which made old saves fail loudly after a bump. The derived check now accepts them.
- **Impact:** After a future bump, pre-5.0 saves load as the current version without the new step's fields, with `addStateDefaults` as the only fallback. The comment, and the F-10 Status reason that repeats it, point the next developer straight at the mistake. This contradicts `paad/config/fix-architecture.md`'s demand that claims be verified.
- **Suggested fix:** Make `migrateFromV4_1ToV5` write the literal `'5.0.0'`; that alone fixes this bug. After the loop in `applyMigrations`, assert `migrated.meta.version === SAVE_FORMAT_VERSION`. The assert does not catch this bug, because the buggy chain also ends at `SAVE_FORMAT_VERSION`. It catches a different mistake: bumping the constant without adding a step. Correct the comment and the F-10 Status reason. Do not add a dummy-step test: `MIGRATIONS` is not injectable, so the test would need a seam that exists only for it.
- **Confidence:** High
- **Found by:** Logic & Correctness, Contract & Integration, Spec Compliance (`claude-opus-5-5`)

### [I2] `setPriceKnowledgeEntry` writes `world.priceKnowledge` around its owner, TradingManager
- **File:** `src/game/state/game-coordinator.js:293-295`; `src/game/state/managers/info-broker.js:51-55`
- **Bug:** The branch adds a coordinator closure, `this.state.world.priceKnowledge[systemId] = entry`, and InfoBrokerManager emits `PRICE_KNOWLEDGE_CHANGED` by hand. The capabilities.js ownership table names TradingManager as the owner of `world.priceKnowledge`. `TradingManager.updatePriceKnowledge` (`trading.js:288-304`) already performs this write and emit, and NavigationManager is already wired to it (`game-coordinator.js:191`). The rewritten capabilities header (lines 47-51) says writes to another manager's slice go through that manager's setter.
- **Impact:** At one of the sites F-5 cited, the branch replaces one ownership bypass with another, and the F-5 Status ("the cited bypasses now go through the slice owners") overstates the fix. There are now two write-and-emit paths for the same slice, and they already differ: `updatePriceKnowledge` copies `prices`, while this path stores the reference. Nothing breaks today, because `priceEntry` is a fresh object.
- **Suggested fix:** Inject `updatePriceKnowledge: (...a) => this.tradingManager.updatePriceKnowledge(...a)` into InfoBrokerManager and call it with `(systemId, priceEntry.prices, priceEntry.lastVisit, priceEntry.source)`, so `InformationBroker` stays the only place those values are set. Drop `setPriceKnowledgeEntry`, its typedef line and the manual emit. Keep InfoBrokerManager's own `markDirty()`, because `updatePriceKnowledge` does not call it.
- **Confidence:** High
- **Found by:** Contract & Integration, Spec Compliance (`claude-opus-5-5`)
