* **Tech stack:** React 18, Vite, plain CSS (rem-variable theme), Three.js starmap behind the panel
* **Files audited:** 1 primary (`src/features/navigation/SystemPanel.jsx`) plus its stylesheets (`css/panel/system-panel.css`, `css/panel/system-info.css`, `css/panel/jump-dialog.css`, `css/variables.css`, `css/base.css`) and the components and hooks it drives (`Modal.jsx`, `DangerWarningDialog.jsx`, `useFocusTrap.js`, `App.jsx` panel wiring)

## Executive Summary

SystemPanel gets the visual basics right:
- Every text colour passes contrast.
- Security level is shown as text as well as colour.
- All controls are native `<button>`s with a visible focus ring.
- Reduced motion is honoured for CSS transitions.

The weak spot is **focus management**:
- Picking a destination from the connected-systems list destroys the focused button and drops focus to `<body>`. That list is the main keyboard route to a jump target.
- Closing the panel or jumping also loses focus.

Further issues:
- The jump error is not announced.
- Connection buttons have very long, noisy names.
- The same jump shows different time and fuel figures in the list and in the target view.

Estimated conformance: **partial AA**. 2.4.3 Focus Order (A) and 4.1.3 Status Messages (AA) fail.

## Impact Summary by User Group

- **Screen reader users:**
  - Choosing a destination silently drops them to the top of the document, and nothing announces the new content.
  - Validation errors are not announced.
  - Each connection button reads out its distance, fuel, time, a "bar chart" emoji and the full event description.
- **Low-vision users:**
  - Text contrast is strong (≥5.5:1 everywhere).
  - The resting border on connection buttons is about 2:1, so they read as plain rows.
  - The sticky header can partly cover a focused item.
- **Colorblind users:** No barrier. Security level is spelled out ("Safe", "Contested", "Dangerous") as well as colour-coded.
- **Motor-impaired users (keyboard/switch/sip-and-puff):**
  - Every action is reachable, but focus is lost after each destination pick, close and jump. Each loss means tabbing back from the top, which is costly for switch users.
  - Escape doesn't close this panel, though every other panel closes on Escape.
  - The desktop close target is about 14×24px.
- **Cognitive and learning disabilities:**
  - "Status:" means "station available" in one view and "on the wormhole network" in the other.
  - The list and the target view disagree on jump time and fuel for the same jump.
  - Abbreviations ("LY", "3d") are unexplained.
  - The critical-damage modal pops up on every target selection.
- **Deaf and hard-of-hearing users:** No audio in this flow. No barrier.
- **Vestibular and photosensitive users:**
  - Panel CSS motion is covered by the global `prefers-reduced-motion` rule.
  - The 3–5s jump camera animation this panel triggers ignores reduced motion. It is out of scope here and is logged in the backlog.

## Serious Issues (Major Difficulty)

### [S1] Choosing a connected system destroys the focused button and drops focus to `<body>`
- **File:** `src/features/navigation/SystemPanel.jsx:351-358` (click handler); `:142` vs `:288` (branch roots); `:76-83` (auto-open modal)
- **Platform:** Web
- **Barrier:** A `.connection-item` calls `selectStarById`, which changes `viewingSystemId`. The component then returns its other branch:
  - The root type changes from `<div>` (current-system view) to a Fragment (target view).
  - React unmounts the whole subtree, and the focused button goes with it. Focus falls to `<body>`.
  - Nothing moves focus into the new content or announces it.
  - If the ship is critically damaged, the auto-opened "Ship Damaged" Modal then records `previous = body` in `useFocusTrap`, so dismissing it sends focus to `<body>` a second time.
- **Criterion:** 2.4.3 Focus Order — Level A
- **Affects:** Keyboard, switch and screen reader users. Star selection on the canvas is mouse-only, so this list is the main keyboard way to pick a jump target. After every pick they have to tab back from the top (skip link, HUD, …) to reach "Jump to System", and screen reader users hear nothing about the new panel content.
- **Fix:** Give both branches the same stable root, and focus the heading whenever the viewed system changes:
  ```jsx
  const headingId = useId();
  const headingRef = useRef(null);
  useEffect(() => { headingRef.current?.focus(); }, [viewingSystemId]);
  // both branches:
  <section className="system-panel" data-panel aria-labelledby={headingId}>
    <div className="system-panel-header">
      <h2 id={headingId} ref={headingRef} tabIndex={-1}>{viewingSystem.name}</h2>
  ```
  Keep `DangerWarningDialog`/`Modal` as siblings that render in both branches (or inside a shared wrapper) so the root type never changes. Focusing the heading also gives the critical-damage modal's focus trap a valid element to restore to. To keep mouse users on the canvas from having focus pulled away, only refocus when focus was inside the panel or on `<body>`.
- **Confidence:** High (92)
- **Found by:** Screen Reader, Keyboard & Motor, Platform Patterns (React)

## Moderate Issues (Friction)

### [M1] Closing the panel or jumping loses focus; it never returns to the opener
- **File:** `src/features/navigation/SystemPanel.jsx:170`, `:292`, `:116`; `src/App.jsx:315-321`, `:326-337`
- **Platform:** Web
- **Barrier:** Focus is lost whenever the panel goes away:
  - The × button and the Jump button unmount the panel while it holds focus. `handleCloseSystemPanel`/`handleJumpComplete` only set `viewingSystemId` to null.
  - On a jump from ORBIT (the normal case), the viewMode focus effect does not re-run, so focus stays on `<body>`.
  - In the DangerWarningDialog "Proceed" path, `useFocusTrap` tries to restore focus to the Jump button, which has already been unmounted.
- **Criterion:** 2.4.3 Focus Order — Level A
- **Affects:** Keyboard and screen reader users lose their place on every close and every jump, and jumping is the core gameplay loop.
- **Fix:**
  - In App, record `document.activeElement` when the panel opens.
  - In `handleCloseSystemPanel`, restore focus to that element if `isConnected`, otherwise call `mainRef.current?.focus()`.
  - In `handleJumpComplete`, call `mainRef.current?.focus()`.
  - Fixing the fallback in `useFocusTrap` (backlog) would cover the dialog path app-wide.
- **Confidence:** High (88)
- **Found by:** Screen Reader, Keyboard & Motor, Platform Patterns (React)

### [M2] Validation error is not announced and not linked to the disabled Jump button
- **File:** `src/features/navigation/SystemPanel.jsx:236-246`
- **Platform:** Web
- **Barrier:**
  - `<div className="validation-message error">` has no `role`.
  - The Jump button is `disabled`, which takes it out of the Tab order, and nothing links it to the error.
  - A screen reader user who tabs through the panel never learns why jumping is unavailable.
  - TradePanel, RefuelPanel, RepairPanel and DialoguePanel all put `role="alert"` on this same pattern, so SystemPanel is the odd one out.
- **Criterion:** 4.1.3 Status Messages — Level AA
- **Affects:** Screen reader users. Sighted users can see the reason just above the button.
- **Fix:**
  ```jsx
  <div id={errId} className="validation-message error" role="alert">{validation.error}</div>
  <button className="jump-btn" onClick={handleJump} disabled={!validation.valid}
          aria-describedby={!validation.valid ? errId : undefined}>
  ```
  Without S1 this is only partly effective, because an alert that is already there when the panel remounts may not be announced.
- **Confidence:** High (82)
- **Found by:** Screen Reader, Platform Patterns (React)

### [M3] Connection buttons have long, noisy accessible names; block content sits inside `<button>`
- **File:** `src/features/navigation/SystemPanel.jsx:351-383` (emoji at `:368`)
- **Platform:** Web
- **Barrier:** The button's name is all of its content joined together, for example "Barnard's Star 6.0 LY bullet 15.0% fuel bullet 3d bar chart Mining Boom at Barnard's Star *(full description)* 4 days remaining".
  - "•" is read as "bullet".
  - "3d" is ambiguous.
  - The inner `<div>`s are not valid content inside a `<button>`.
- **Criterion:** No strict WCAG failure, since a name exists and describes the purpose. It is a serious usability problem for screen reader users (related to 2.4.6 Headings and Labels, AA).
- **Affects:** Screen reader users hear a paragraph on every Tab. Cognitive users face the same overload.
- **Fix:**
  ```jsx
  <button className="connection-item" aria-describedby={`conn-${system.id}-details`} ...>
    <span className="connection-name">{system.name}</span>
    <span id={`conn-${system.id}-details`} className="connection-details">
      {distance} light-years, {fuel}% fuel, {days} day{s}
    </span>
    ...<span className="event-icon" aria-hidden="true">📊</span>
  ```
  Switch the inner `div`s to `span`s styled `display:block`.
- **Confidence:** High (80)
- **Found by:** Screen Reader, Platform Patterns (React), Cognitive & Learning

### [M4] "Status:" means different things in the two views, and destination station availability is never shown
- **File:** `src/features/navigation/SystemPanel.jsx:199-206` vs `:321-326`
- **Platform:** Web
- **Barrier:** In the current-system view, "Status:" means Station Available / No Station. In the target view, the same label means On / Off the wormhole network. A player choosing a destination can't see whether it has a station, and may take the wormhole status as the station answer.
- **Criterion:** No strict WCAG failure (3.2.4 is about components with the same function, not about reusing a label). This is a cognitive best practice.
- **Affects:** Users with memory or learning disabilities who rely on a label always meaning the same thing. It affects every player when planning refuels.
- **Fix:** Use two distinct labels, "Station:" and "Wormhole network:", and render both rows in both views. Pull the shared rows into one `SystemDetails` sub-component.
- **Confidence:** High (85)
- **Found by:** Cognitive & Learning

### [M5] The same jump shows different time and fuel figures in the list and the target view
- **File:** `src/features/navigation/SystemPanel.jsx:276`, `:362-363` vs `:217-230`
- **Platform:** Web
- **Barrier:** The list and the target view compute and format the same jump differently:
  - Time: the list uses `calculateJumpTime(distance)`, which ignores engine condition. The target view uses `validateJump` → `calculateJumpTimeWithCondition` (`game-navigation.js:139-149`, `:347`). With a worn engine, the list says "2d" and the target view says "3 days".
  - Fuel: the list shows `toFixed(1)` ("15.6%") and the target view shows `Math.round` ("16%").
  - This also breaks the CLAUDE.md rule to round at the calculation layer: `calculateFuelCostWithCondition` returns raw floats and the JSX rounds them inline in two different ways.
- **Criterion:** None (a correctness bug with cognitive impact)
- **Affects:** Users with dyscalculia or memory impairments, who can't tell which figure is right. All players get a wrong time estimate when the engine is worn.
- **Fix:**
  - In the list, use `game.navigationSystem.calculateJumpTimeWithCondition(distance, engineCondition)`.
  - Round fuel once (`Math.round`) at the calculation layer.
  - Write "N day(s)" in both places.
- **Confidence:** High (90)
- **Found by:** Cognitive & Learning

## Minor Issues & AAA Recommendations

**Minor issues:**
- **[m1]** The panel root (`SystemPanel.jsx:167`, `:289`) is an unnamed `<div>`. Make it a `<section aria-labelledby>`, as part of the S1 fix. *(1.3.1 best practice)*
- **[m2]** The panel title is `<h3>` (`:169`, `:291`) while sibling panels (Refuel, Trade, ActiveMissions) use `<h2>`. Change it to `<h2>` and update `css/panel/system-panel.css:35`. *(1.3.1 best practice)*
- **[m3]** The `.system-stars` `<ul>` has `list-style:none` (`css/panel/system-panel.css:98-103`), so Safari/VoiceOver drops its list semantics. Add `role="list"` at `SystemPanel.jsx:21`. *(1.3.1 best practice)*
- **[m4]** The connections list (`:330-386`) has no heading and isn't a `<ul>`. The buttons also look like more property rows to sighted users. Add a "Wormhole Connections" heading and a `<ul>`/`<li>`. *(1.3.1 / 2.4.6 best practice)*
- **[m5]** The close button's `aria-label="Close"` (`:170`, `:292`) is generic when other "Close" buttons may be on screen. Use ``aria-label={`Close ${viewingSystem.name} panel`}``. *(2.4.6 AA, weak)*
- **[m6]** Escape doesn't close SystemPanel, but PanelContainer, `useClickOutside` panels and Modal all close on Escape. Add an Escape `onKeyDown` handler on the panel root, scoped so it doesn't clash with Modal. *(consistency; not a 2.1.2 trap)*
- **[m7]** The resting border on `.connection-item` is `rgba(0,255,136,0.3)`, about 2.0:1 (`css/panel/system-panel.css:203-213`). The bold green name looks the same as the property labels, so this border is almost the only button cue. Raise it to `rgba(0,255,136,0.6)` (about 4:1). *(1.4.11 AA, borderline)*
- **[m8]** A failed jump gives no feedback (`:122-130`). The `{success:false}` result of `executeJump` is ignored, the catch only logs to the console, and the panel is already closed. It is only reachable through a race. Show the error through the existing `aria-live` NotificationContainer. *(no strict criterion)*
- **[m9]** "Insufficient fuel for jump" and "No wormhole connection to target system" (`src/game/game-navigation.js:316`, `:357`) give no remedy. Add "Refuel at a station" and "Route through a connected system". *(3.3.3 AA, arguable)*
- **[m10]** The critical-damage modal always says "Dock at a station for repairs" (`:159`), even when the current system has no station. Branch the text on `currentSystem.st > 0`. *(cognitive best practice)*

**AAA recommendations:**
- **[AAA] [m11]** The desktop close button is about 14×24 CSS px (`css/panel/system-panel.css:41-52` sets `padding:0`). It reaches 44px only below 600px wide. Add `min-width:44px; min-height:44px`. *(2.5.5 AAA; 2.5.8 AA passes via the spacing exception)*
- **[AAA] [m12]** The sticky header (`css/panel/system-panel.css:22-33`) can partly cover a focused connection item on Shift+Tab. Add `.system-panel { scroll-padding-top: 4rem; }`. *(2.4.12 AAA; 2.4.11 AA passes)*
- **[AAA] [m13]** The critical-damage modal reopens on every target selection while damaged (`:76-83`), even though the inline error already says the same thing. Show it once per damage state. *(2.2.4 AAA)*
- **[AAA] [m14]** Jargon and abbreviations: "LY", "3d", bare spectral codes (`starKind()` only shows for multi-star systems), "Wormholes: 3", and security levels with no description. Use `<abbr title="light-years">`, write "days" in full, and show the zone description. *(3.1.3 / 3.1.4 AAA)*

**Non-a11y bug found in the audited file:**
- `onClick={onClose}` at `:170` and `:292` passes the click event as `keepSelection` to `handleCloseSystemPanel(keepSelection = false)` (`src/App.jsx:315`). The event object is truthy, so `deselectStar()` never runs and the selection ring stays visible after ×. Fix: `onClick={() => onClose()}`. Confidence: 95.

2. **`role="alert"` + `aria-describedby` on the validation error and Jump button**, matching Trade/Refuel/Repair. Fixes M2. *Effort: small.*
3. **Tidy the connection button**: `aria-hidden` on 📊, `aria-describedby` for the details, `span`s instead of `div`s, and "days" in full. Fixes M3 and part of m14. *Effort: small.*
4. **Use `calculateJumpTimeWithCondition` + `Math.round` fuel in the list** so both views agree. Fixes M5. *Effort: small.*
5. **Restore focus on close/jump in App** (record the opener, fall back to `mainRef`). Fixes M1. *Effort: small.* Also fix `onClick={() => onClose()}` while there.
